## Anti-Patterns Verdict

**LLM assessment:** Not AI slop. The rail is a genuinely persistent typographic column, not a sidebar template; labels are domain-specific ("catalogue," "onward," "well") rather than generic ("Menu," "Next"); there's no icon library, gradient underline, or pill button anywhere in the nav CSS. `.rail-num[aria-current="step"]::after` cuts a 3px bar into the rail's own border to fake a physical tab notch — the kind of considered detail generic output doesn't produce. Reads as authored.

**Deterministic scan:** `detect.mjs --json` ran clean against all 15 nav-related files (`Workspace.tsx`, `Cover.tsx`, `Spine.tsx`, `Catalogue.tsx`, `NextRecord.tsx`, `PageTransition.tsx`, `Foot.tsx`, `ThemeToggle.tsx`, `ShelfView.tsx`, `Record.tsx`, `Chapter.tsx`, `FolderPage.tsx`, and the three route files) — zero findings, exit 0. A manual DOM sweep (`border-left`/`border-right` accents, `<hr>` usage) also came back clean on both `/` and `/vpro`. The scan did **not** catch two things a static rule-check can't see: a measured WCAG contrast near-miss and a live keyboard-trap edge case — both below.

**Manual/measured evidence (Assessment B, via a live dev-server + Playwright driver, not guesses):**
- `.onward-up` / `.onward-key` (the small labels on the record-route end-of-page pager) measure **4.39:1** against their background — under WCAG AA's 4.5:1 floor for normal-size text. Resolved via the browser's own color engine (canvas round-trip on the reported `oklab()` value), not hand math.
- Catalogue `<dialog>`: tabbing through all 8 focusable elements inside it, the Tab press after the last element landed on `document.body` for exactly one step before the next Tab correctly returned to the dialog's first element. Escape-to-close and re-entry both work; this is a one-keystroke containment gap at the wrap boundary, not an escape from the modal.
- 7 border-bottom hairlines found on the index (`.well`, `.page-frame.cover`, `.shelf-face` ×3, `.slot` ×2), all 1px Line-token color, all scoped to the ~937px content column rather than the full 1440px viewport — none read as a full-width section/chapter divider, but the shelf/slot instances are row separators inside the drawer's list and are worth weighing against the "no ink dividers" hard rule as a judgment call, not a clear violation.
- Focus-visible outlines (2px solid rose) confirmed present on every traced nav element on both pages. Mobile rail/spine confirmed collapsing to a horizontal strip (not hidden, not overflowing) at 390px/428px. No horizontal scroll on `<body>` at any tested width.

**Visual overlays:** Script injection into the live page was confirmed working (mutation preflight passed), but the bundled `/detect.js` 404'd — this project doesn't serve it at that path — so no in-page overlay actually rendered. No user-visible overlay is available from this run; the findings above come from direct DOM/computed-style queries instead.

## Overall Impression

The navigation is the strongest-executed part of the system: the Rail/Spine unification that CLAUDE.md flagged as a real risk ("two navigation systems... unified rather than kept divergent") is genuinely shipped, not just claimed — same classes, same DOM order, same keyboard contract. The biggest opportunity is closing two small, concrete gaps: one hard-rule violation (pink sitting at rest in the drawer, the frame's supposed calm resolution) and one measured accessibility regression of the exact class the project has already been burned by once (PRODUCT.md documents fixing a 2.06:1 contrast failure and calls that "a regression... if it reappears" — a second, smaller instance just did, at 4.39:1). Neither is hard to fix; both are worth fixing before they compound.

## What's Working

1. **The Spine/Rail unification is real.** `Spine.tsx` and `Workspace.tsx`'s rail share `.rail-mark`/`.rail-up`/`.rail-key`/`.rail-nums`/`.rail-num`/`.rail-pos` and a shared `roving()` keyboard contract — the settled 2026-07-31 decision to stop treating them as two nav languages actually landed in code.
2. **`neighbours()` + null-guard pagination** (`lib/schema.ts`, used by `NextRecord.tsx`) solves "never dead-end the pager" once, centrally, instead of per call site — and `NextRecord` returns `null` outright rather than rendering a self-pointing pager when there's nothing to page to.
3. **The Catalogue leans on the platform.** Using native `<dialog>` for focus/Escape/backdrop instead of a hand-rolled trap is the right call, and it's nearly airtight — the one edge case Assessment B measured is a single-keystroke wrap-boundary glitch, not a broken modal.

## Priority Issues

**[P1] `.shelf-key` puts the site's interaction pink at permanent rest in the drawer**
Why it matters: `globals.css` sets `.shelf-key { color: var(--mark-ink) }` unconditionally — no `:hover`, `:focus-visible`, or `[aria-current]` gate — so all three real compartments (`01-vpro`, `02-the-stacks`, `03-motion-dime`) show a permanently pink label in the drawer, on every visit. This directly contradicts CLAUDE.md's hard rule that pink is "absent at rest" and exists "only as the reward for interacting" — and it lands in the one screen (the drawer) that's meant to read as the frame's calm resolution, not its most rule-violating surface. An adjacent code comment even describes the intended gated behavior; the selector just doesn't implement it.
Fix: gate `.shelf-key`'s color the same way `.comp-key`/`.rail-num` already do — mute at rest, promote to `--mark-ink` only on `:hover`/`:focus-visible` (the hover hook already exists via `.shelf::after`).
Suggested command: `/impeccable polish`

**[P1] Record-route pager text fails WCAG AA contrast — the same failure class already flagged once**
Why it matters: `.onward-up`/`.onward-key` (the small labels on `NextRecord`'s end-of-page pager) measure 4.39:1 against their background, under the 4.5:1 floor for normal-size text. PRODUCT.md already documents fixing an earlier, worse instance of this exact bug class (a 2.06:1 "coming" label) and explicitly calls it "a regression, not a style choice, if it reappears." This is a second, smaller instance.
Fix: darken the label color one step (toward `--muted-strong`), the same Board-Text Exception already used elsewhere in the system for text sitting on a darker ground.
Suggested command: `/impeccable audit`

**[P2] Folder-tab click and "Read more →" are indistinguishable as actions**
Why it matters: clicking a 00–03 tab swaps an in-place preview; only "Read more →" actually navigates. Tabs are one of the web's strongest "I'm now looking at this content" conventions, so a first-time visitor can reasonably believe they've read a chapter after a tab click and never discover the real content behind "Read more." CLAUDE.md itself flags this exact ambiguity as an open, unresolved call (§1e) — the current build hasn't added any signal to close it, even a minimal one.
Fix: a small, quiet "previewing" or "level 1 of 5" cue near the tab row — in-register, no new chrome.
Suggested command: `/impeccable clarify`

**[P2] Catalogue dialog has a one-keystroke focus-containment leak at the tab-order wrap boundary**
Why it matters: tabbing past the dialog's last focusable element lands focus on `document.body` for exactly one Tab before the next Tab correctly returns to the first element inside the dialog. Escape-to-close and re-entry both work, so this isn't a broken modal, but it's a measured deviation from a fully contained focus trap that a keyboard-only user would notice.
Fix: verify the roving/native trap logic at the dialog's last-element boundary; re-confirm in a real browser (this was measured via a Playwright-driven Chromium instance, so it's worth a manual re-check before treating it as definitively cross-browser).
Suggested command: `/impeccable audit`

**[P3] CLAUDE.md §1a describes a scroll-driven chapter mechanism the code has already replaced**
Why it matters: the "boundary-slide, not pinned scroll-hijack" rule in CLAUDE.md describes chapters stacking in one continuous scroll. `Record.tsx`'s own docblock confirms chapters moved to separate per-route pages a while ago; chapter-to-chapter movement is now prev/next links and Spine clicks through `PageTransition`'s exit-then-push handoff, not scroll position. The routed approach is arguably a stronger fix (it removes the scroll-jack risk class entirely rather than managing it), but the spec and the shipped nav now disagree, which risks a future contributor "fixing" the nav back toward a mechanism that no longer exists.
Fix: not a code change — update CLAUDE.md §1a to describe the route-based reality.
Suggested command: none (documentation-only; flag for Natasha)

## Persona Red Flags

**Alex (Power User):** Keyboard support is genuinely strong for a portfolio site — full roving-tabindex with Home/End on both tablists, real anchor semantics everywhere. What Alex won't get: no accelerator keys for jumping between records/chapters, and no visible affordance that the Catalogue exists until reaching a record page and spotting the "catalogue" button in the Spine's foot — a power user deep-linked straight to `/vpro/02` has to scroll the Spine to discover the jump-anywhere panel exists at all.

**Sam (Accessibility):** Strong marks — native `<dialog>` correctly delegates focus-trap/Escape/backdrop to the platform (with one measured one-Tab wrap-boundary leak, see P2 above); `.vh` visually-hidden spans preserve full compartment/chapter names for screen readers even when the sighted UI collapses to a bare numeral; `aria-current`/`aria-selected` used correctly and consistently; the skip link targets a stable `#content` anchor that exists on every route type. The one real gap Sam hits: the measured 4.39:1 pager-label contrast (P1 above) — small enough to matter for low-vision users specifically, distinct from the `.shelf-key` pink-at-rest issue, which is a brand-consistency problem for a sighted return visitor rather than an accessibility one.

## Minor Observations

- `Cover.tsx`'s in-folder pager dead-stops via native `disabled` while `NextRecord`'s cross-record pager wraps around — two different affordance philosophies for visually similar controls, with no in-UI explanation. Possibly intentional (folders have a real fixed order; records loop), but worth a deliberate note somewhere so it doesn't look like an inconsistency later.
- A stale comment in `globals.css` on `.slot` claims the "coming" tabs (Writing/Reading) are "inert by construction: not a button, no handler, nothing to click" — but `Workspace.tsx` wraps each slot in a real `<GoLink>` with working hover/focus-visible states. The link behavior is correct (an empty state that isn't a dead end, per §1c), but the comment actively misdescribes it and will mislead the next person to touch the file.
- `Catalogue.tsx` and `NextRecord.tsx` both independently re-derive "records only, filter out shelves" — small duplication, not urgent.
- `.comp-key` (the pink "Record 01" label) measures a healthy 5.35:1 — the system's contrast discipline is generally sound; the two P1/P2 misses above are the exceptions, not the pattern.
