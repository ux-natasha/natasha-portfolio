LEVEL 2 — WHAT WE INHERITED

The old application had about a decade of history and one prior revamp, done by an outsourced design company. It showed a network of connections between tasks — what depended on what — but not the thing consultants actually asked for: when a task should have started, and by how much it had slipped.

The code had aged into a small number of people who could read it. A simple config change took two days. A hidden column took another. That, plus scheduling runs that took hours, is what got the rebuild approved.

I patched it for a year first — a progress bar on running tasks, the critical path visualisation, and document upload. Maintaining it is how I learned the theory it was built on, which is older than I am.

I learned the system by keeping it alive, then got to help replace it.

LEVEL 2 — WHAT IT IS

Configuration is the part of the system that exists before any project does. Attributes, workflows, reasons, holidays — the definitions everything else runs on. Nobody demos it. Every other module depends on it.

In the system we replaced, those definitions lived in code, behind the four people who understood that code. Changing one was a request, a queue, and two days of someone else's time. Getting a hidden column back was another day. For a company with "digital lab" in the name, that was a hard thing to keep explaining.

Admin was built first — the company develops in chunks, tests them in isolation, then adds a layer. So this module carried a second job beyond its own: it was where the table got its structure and where the component library got settled. Those decisions went on to hold up every screen after it.

The two days became a screen you open yourself.

LEVEL 2 — THE HARDEST ONE

Users didn't want a network of connections. They wanted to see how a delay moved a date. This is the module where the team had the most iterations, including changes of scope and concept — seven or eight fully working, multi-user-journey prototypes before one settled. The one that lived is the planning screen.

For a project manager, a project is a document. On a web app with no autosave, losing one means someone gets yelled at. A designer can't fix the backend — what a designer can do is take friction out of the interface so the risk never gets taken. So: save-as-draft big and prominent, tasks addable several ways, and the very little space left spent pointing at what actually matters.

I read everything I could — ClickUp, Zoho, Atlassian, Word, Excel, MS Project — toolbars, gantt interactions, how tasks get added, deleted, nested. The gantt was the piece that, if bad, would break the product.

A UI designer might want a beautiful screen. A project manager will not.

LEVEL 2 — THE ONE I DIDN'T CRACK

Tasks was hard in a way the gantt wasn't. The gantt was new and bright and nobody had expectations. Tasks was known, well used, and most people didn't want it changed at all — while the team believed it could still be better. I couldn't judge how much change the system would tolerate.

So I tried things. Converting the old design across. Adding colour. Splitting it into separate pages. Cutting columns. None of it clicked. It clicked when a then-senior colleague designed the landing: a taller row height, plus the divider we'd already built in admin. Small, and it just worked.

The insight that survived from the discussions was about people, not pixels: what you see depends on who you are. Someone who updates a task gets Task Updates. A project manager or parent-task manager gets Task Reviews — they aren't making progress, they're judging it.

Someone else turned the key. The corner behind the door was mine.
